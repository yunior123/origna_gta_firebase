## CRITICAL — Fix Before Launch (money bugs / security holes)

### C-1 [PAYMENT] `process_charge_refunded` never restores stock
**File:** `functions/handlers/payment_stripe.py:3137-3161`
After a Stripe Dashboard refund, stock is permanently lost. `process_async_payment_failed` and `process_session_expired` both restore stock — `process_charge_refunded` does not.
**Fix:** Call `_restore_stock_for_order(order_data)` and set `Fields.STOCK_RESTORED: True` in this handler.

### C-2 [PAYMENT] Dispute won re-transfer always gets `seller_stripe_id = None`
**File:** `functions/handlers/payment_stripe.py:3577`
```python
# BUG: seller_stripe_accounts stores seller_id -> "acct_xxx" (string), not a dict
seller_stripe_id = seller_stripe_snapshot.get(seller_id, {}).get(Fields.STRIPE_ACCOUNT_ID)
# FIX:
seller_stripe_id = seller_stripe_snapshot.get(seller_id)
```
Defeats the entire snapshot security feature. Re-transfers after won disputes go to the live account (post-swap attacker), not the checkout-time account.

### C-3 [PAYMENT] Async payment path never sets order status to CONFIRMED
**File:** `functions/handlers/payment_stripe.py:2512`
`process_async_payment_succeeded` (Interac/bank transfers) only sets `paymentStatus=CAPTURED` but never sets `orderStatus=CONFIRMED`. These orders are permanently stuck in `PENDING`.

### C-4 [PAYMENT] Cron auto-payout re-derives fee rate via division (floating-point drift)
**File:** `functions/handlers/cron_jobs.py:373-378`
Cron uses `stored_fee_total / order_subtotal` instead of reading `Fields.PLATFORM_FEE_RATIO` directly. Produces cent-level discrepancies vs the webhook payout path. Fix: use `order_data.get(Fields.PLATFORM_FEE_RATIO, PLATFORM_FEE_RATIO)`.

### C-5 [AUTH] `_buildActionButton` reads seller Stripe status from wrong collection
**File:** `origna_gta/lib/screens/seller_registration_screen.dart:326-328`
Reads `onboardingCompleted`, `payoutsEnabled` from `UserModel` (users/{uid}), but backend writes these to `seller_profiles/{uid}` exclusively. Button logic will never see correct state — sellers who completed onboarding still see "Start Registration".

### C-6 [AUTH] `UserModel.fromMap` maps Stripe fields from `users/{uid}` (always null/false)
**File:** `origna_gta/lib/models/models.dart:1043-1046`
Fields `stripeAccountId`, `payoutsEnabled`, `chargesEnabled`, `onboardingCompleted` in `UserModel` map from `users/{uid}` which no longer stores them. Ghost data throughout the app.

### C-7 [SECURITY] Sellers can self-set `isTrending` via Firestore rules
**File:** `firestore.rules:338-356`
Comment says "Admin-only toggles (not editable by sellers)" but the rule condition allows product owners (sellers) to write `isTrending` and `trendingAt`. Sellers can self-promote.
**Fix:** Add `(isAdmin() || !request.resource.data.diff(resource.data).affectedKeys().hasAny(['isTrending', 'trendingAt']))`.

### C-8 [ORDER] Cancel + capture race condition (no shared transaction)
**File:** `functions/handlers/orders.py` + `functions/handlers/payment_stripe.py`
Both cancel and capture read `order.status` without coordinating transactions. Concurrent cancel+capture → customer refunded AND seller paid.

### C-9 [CRON] Auto-confirm is not idempotent — seller metrics double-incremented on retry
**File:** `functions/handlers/cron.py` — `auto_confirm_orders`
No transaction check on `status == 'delivered'` before confirming. Crash mid-batch → next run re-confirms, doubling seller metrics/payout triggers.

### C-10 [CRON] Void expired auth races with capture (charge + void simultaneously)
**File:** `functions/handlers/cron.py` — `void_expired_authorizations`
Seller confirms shipment at same moment cron voids → customer charged AND auth voided.

## HIGH — Must Fix Before Launch

### H-1 [PAYMENT] Double payout risk: webhook and cron use different idempotency keys
**File:** `payment_stripe.py:2466`, `cron_jobs.py:482`
Webhook uses `transfer_{order_id}_{seller_id}`, cron uses `auto_transfer_{order_id}_{seller_id}`. Stripe accepts both — seller gets double payout.
**Fix:** Unify to one key format across both paths.

### H-2 [PAYMENT] Checkout product docs fetched sequentially (not batched)
**File:** `functions/handlers/payment_stripe.py:745-748`
10-item cart = 10 serial Firestore reads (~300-800ms). Replace with `get_all([refs])`.

### H-3 [AUTH] `pending_profiles` rules reject `name`+`updatedAt` that client writes
**File:** `firestore.rules:716-720` + `origna_gta/lib/core/repositories/auth_repository.dart:356-364`
Rules only allow `marketingOptIn` on create. Client writes `name`+`updatedAt` via `set(merge:true)` (which is an update, not create). Names are silently dropped in production.

### H-4 [AUTH] `create_user_profile` has no rate limiter (billing attack)
**File:** `functions/handlers/users.py:41`
Can be called directly without going through Firebase Auth's rate limiting. Add `RateLimiter` with `fail_closed=True`.

### H-5 [PAYMENT] `process_async_payment_succeeded` skips all product/amount validation
**File:** `functions/handlers/payment_stripe.py:2489-2544`
Async payment path skips seller suspension checks, product deactivation checks, and amount verification that the sync path does.

### H-6 [CRON] Rate limiter cleanup — no pagination (will timeout at scale)
**File:** `functions/handlers/cron.py` — `cleanup_rate_limiters`
Unbounded Firestore query. At 100K users → timeout, growing rate limit collection.

### H-7 [CRON] No error isolation between batch items (one bad order blocks all)
**File:** `functions/handlers/cron.py` — all batch handlers
Single exception stops processing of all remaining items. Wrap each in try/except.

### H-8 [CRON] `deliveredAt` not validated as server timestamp → return window bypass
**File:** `functions/handlers/cron.py` + `functions/handlers/orders.py`
Seller can set `deliveredAt` to past date → immediate auto-confirm → buyer loses 3-day dispute window.

### H-9 [PERFORMANCE] `compute_seller_metrics` N+1 query (1 query per seller)
**File:** `functions/handlers/cron_jobs.py:1663-1676`
10K sellers = 10K separate Firestore queries. Invert: query all orders once, group by seller in Python.

### H-10 [PERFORMANCE] `boto3` imported at module level (cold start tax)
**File:** `functions/handlers/products.py:20`
~200ms cold start penalty for every product function invocation. Move inside `_get_cached_s3_client()`.

### H-11 [ORDER] State machine — no check preventing backward transitions
**File:** `functions/handlers/orders.py`
No `VALID_TRANSITIONS` guard — `confirmed` → `delivered` is possible. Add an explicit state machine dict.

### H-12 [ORDER] Double-payout risk on order confirmed (missing idempotency key on payout)
**File:** `functions/handlers/payment_stripe.py` — payout handler
Payout triggered on status → `confirmed`. If status change fires twice, seller gets double payout.

## MEDIUM — Fix Soon

### M-1 [SECURITY] `calculate_shipping_cost` has no auth check
**File:** `functions/handlers/shipping.py:9`
Unauthenticated callers can enumerate addresses at scale, exhaust Geoapify quota (denial-of-wallet). Add `if not req.auth: raise HttpsError("unauthenticated", ...)`.

### M-2 [SECURITY] Unauthenticated calls bypass Firestore rules via Admin SDK
**File:** `functions/handlers/products.py:2725` (`get_product_ratings_paginated`)
Firestore rule requires `isAuthenticated()` for rating reads, but CF uses Admin SDK and allows unauthenticated calls. Design inconsistency — decide and enforce consistently.

### M-3 [AUTH] No MFA enforcement for sellers with active Stripe payouts
Compromised seller account → payout redirect via Stripe Dashboard. Post-launch work.

### M-4 [AUTH] `create_connect_account` rate limiter uses `fail_closed=False`
**File:** `functions/handlers/payment_stripe.py:3842`
Financial/Stripe-creating operation should use `fail_closed=True`.

### M-5 [PAYMENT] Partial refund uses wrong denominator (total vs subtotal)
**File:** `functions/handlers/payment_stripe.py:3021`
Transfer reversal calculation divides by `amount_total` (includes tax/shipping) instead of `subtotal`. Seller keeps more than they should on partial refunds.

### M-6 [PAYMENT] `biometricOnly: true` blocks PIN-only devices at checkout
**File:** `origna_gta/lib/features/checkout/checkout_provider.dart:313`
Devices without biometrics fail checkout for orders >$100. Change to `biometricOnly: false`.

### M-7 [CRON] Auto-confirm ignores active return requests
**File:** `functions/handlers/cron.py`
Cron confirms order while buyer's return request is still open. Add check for active return requests before auto-confirm.

### M-8 [PERFORMANCE] `cleanup_orphaned_r2_images` reads entire products collection
**File:** `functions/handlers/cron_jobs.py:945`
No `.limit()` — at 1M products = $219/year just for this cron. Paginate at 500.

### M-9 [PERFORMANCE] Checkout product pre-load sequential (frontend)
**File:** `origna_gta/lib/features/checkout/checkout_provider.dart`
(See H-2 for backend — same pattern issue on frontend side for pre-validation.)

### M-10 [PERFORMANCE] `cartItemQuantityProvider` creates N separate Firestore listeners
**File:** `origna_gta/lib/features/cart/cart_provider.dart:93-107`
10-item cart = 10 concurrent WebSocket connections. Derive from existing `cartItemsProvider` stream.

### M-11 [PERFORMANCE] `searchQueryProvider` and `selectedCategoryProvider` not autoDispose
**File:** `origna_gta/lib/features/products/products_provider.dart:109,112`
State leaks on navigation away. Add `.autoDispose`.

### M-12 [PERFORMANCE] Stripe PaymentIntent.retrieve called per-seller in cron loop
**File:** `functions/handlers/cron_jobs.py:206,433`
250 orders = 250 sequential Stripe API calls = 50s (near 60s timeout). Use `ThreadPoolExecutor(max_workers=10)`.

### M-13 [ORDER] Cron auto-confirm bypasses active return requests
Same as M-7.

### M-14 [CRON] Missing alerting on cron failure
Silent failures. Add Cloud Monitoring alert or write to `cron_failures` collection.

### Honest Verdict
The payment pipeline security is strong (HMAC verified, prices re-fetched, self-purchase blocked, idempotency present). The **critical bugs are logic/data bugs, not auth holes**. C-1 through C-4 are money bugs that will silently misbehave in production. C-5/C-6 are a critical UX regression where the seller onboarding screen will never show the correct state. Fix these 10 criticals before launch.
